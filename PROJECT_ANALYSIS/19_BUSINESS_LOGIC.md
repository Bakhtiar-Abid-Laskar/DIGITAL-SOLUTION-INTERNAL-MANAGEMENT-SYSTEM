# RepairShop — Business Logic Documentation

## 1. Job Code Generation

### Rule: Server-Side Only
Job codes are NEVER generated in client code. They are exclusively generated by PostgreSQL.

### Algorithm
```
Format: RS-{YYYY}-{NNNN}
  RS   = RepairShop prefix (fixed)
  YYYY = Current calendar year (4 digits)
  NNNN = Sequence number, zero-padded to 4 digits (monotonically increasing)

Examples:
  RS-2026-0001 (first job of 2026)
  RS-2026-0042 (42nd job created across all time)
  RS-2027-0043 (next year, sequence continues from 43 — does NOT reset per year)
```

### Implementation
```sql
CREATE SEQUENCE IF NOT EXISTS job_code_seq START 1;

CREATE OR REPLACE FUNCTION public.generate_job_code()
RETURNS TEXT AS $$
DECLARE
  code TEXT;
BEGIN
  code := 'RS-' || TO_CHAR(NOW(), 'YYYY') || '-' || LPAD(nextval('job_code_seq')::TEXT, 4, '0');
  RETURN code;
END;
$$ LANGUAGE plpgsql;
```

Called by client: `supabase.rpc('generate_job_code')`

### Why Server-Side?
Prevents duplicate codes in concurrent job creation scenarios. If two receptionists create jobs at the exact same millisecond, the PostgreSQL sequence guarantees atomically different values.

## 2. Job Status State Machine

### States
```
           ┌─────────────────────────────────────┐
           │                                     │
           ▼                                     │
       [Received] ──────────────► [In Progress]  │
                                       │         │
                                       │    [Waiting for Materials]
                                       │         │
                                       └─────────┤
                                                 │
                                                 ▼
                                           [Completed]
```

### Rules
- **Received** → Initial state on job creation (automatic)
- **In Progress** → Set by Technician when starting work
- **Waiting for Materials** → Set by Technician when awaiting parts
- **Completed** → Set by Technician when repair is done
  - Also sets `completed_at = current timestamp`
  - Locks all editing on the job (read-only for technician)

### Who Can Change Status
| From → To | Mobile (Tech) | Mobile (Recept) | Admin Web |
|---|---|---|---|
| Any → In Progress | ✅ | ✅ | ✅ |
| Any → Waiting | ✅ | ✅ | ✅ |
| Any → Completed | ✅ | ✅ | ✅ |
| Any → Received | ❌ | ✅ | ✅ |

> Technicians cannot revert a job back to "Received" (receptionist/admin can if needed).

## 4. Billing Formula

### Confirmed Formula
```
parts_total  = SUM(job_materials.total_cost)    [sum of all parts used]
labour_charge = receptionist input (₹)          [manual entry]
tax_percent   = receptionist input (%)          [default: 18%]
discount      = receptionist input (₹)          [manual entry, default: 0]

subtotal      = parts_total + labour_charge
tax_amount    = subtotal × (tax_percent / 100)
grand_total   = subtotal + tax_amount - discount
             = (parts_total + labour_charge) × (1 + tax_percent / 100) - discount
```

### Verification Example
```
Input:
  parts = ₹500
  labour = ₹300
  tax = 18%
  discount = ₹50

Calculation:
  subtotal = 500 + 300 = 800
  tax_amount = 800 × 0.18 = 144
  grand_total = 800 + 144 - 50 = 894

Expected output: ₹894 ✓
```

### Rounding
All money values rounded to 2 decimal places:
```typescript
Math.round(value * 100) / 100
```

### Where the Formula Lives
1. `admin-panel/src/utils/billing.ts` — `calculateGrandTotal()` function
2. `RepairShopApp/src/utils/billing.ts` — identical copy
3. `admin-panel/src/shared/documents/DocumentRenderer.ts` — used for document generation
4. Admin panel Job Detail page (billing tab) — inline calculation for live preview

## 5. Salary Calculation Formula

### CONFIRMED Formula (from GEMINI.md)
```
present_pay      = present_days × base_daily_rate
halfday_pay      = halfday_count × (base_daily_rate / 2)
leave_pay        = 0  (leave does not get paid)
ot_pay           = ot_hours × ot_rate_per_hour
early_deduction  = early_hours × early_deduction_per_hour
gross_salary     = present_pay + halfday_pay + ot_pay - early_deduction
advance_deducted = SUM(payments.amount)
                   WHERE type = 'advance_salary'
                   AND user_id = X
                   AND month = YYYY-MM
net_salary       = gross_salary - advance_deducted
```

### Input Values Source
| Input | Source |
|---|---|
| `present_days` | COUNT(attendance WHERE status = 'Present' AND month = X) |
| `halfday_count` | COUNT(attendance WHERE status = 'Halfday' AND month = X) |
| `ot_hours` | SUM(attendance.ot_hours WHERE month = X) |
| `early_hours` | SUM(attendance.early_hours WHERE month = X) |
| `base_daily_rate` | `staff_rates.base_daily_rate` |
| `ot_rate_per_hour` | `staff_rates.ot_rate_per_hour` |
| `early_deduction_per_hour` | `staff_rates.early_deduction_per_hour` |
| `advance_deducted` | SUM(payments WHERE type='advance_salary' AND month=X) |

### Working Days
The `working_days` input in `SalaryCalculatorForm` is the total business days in the month (provided by admin — accounts for holidays). It's used to compute:
```
absent_count = working_days - present_days - halfday_count - leave_count
```
`absent_count` is stored but does NOT affect net_salary directly (absent days simply have no `present_pay`).

### Advance Salary Scope
Advance salary deducts from the **same month only**. Advances from previous months are NOT carried forward unless the admin manually records another advance payment for the current month.

## 6. Attendance Status Logic

### Attendance Status Determination
The `status` field in the attendance table can be:

| Status | Criteria |
|---|---|
| `Present` | Checked in on time, checked out (or full day worked) |
| `Halfday` | Checked in, but early departure (early_hours > 0) |
| `Leave` | Manually marked by admin (not via check-in/out) |
| `Absent` | No record for the date OR manually marked absent |

### OT Hours Calculation
OT hours (`ot_hours`) are currently stored but the logic for when they're set is handled by the admin or by the check-out time difference calculation. The specific cut-off time for OT needs business confirmation.

### Early Departure Calculation
Early hours (`early_hours`) are calculated based on departure time vs. expected end-of-shift time. The expected shift end time is a business rule that should be documented separately.

## 8. Phone Number Normalization

### Indian Phone Number Rules
All customer contact numbers stored in `jobs.customer_contact` should be normalized.

### Normalization Algorithm
```
Input variations:
  "9876543210"       → 10-digit, no prefix
  "09876543210"      → 11-digit, leading 0
  "919876543210"     → 12-digit, with country code
  "+919876543210"    → 13-character, with + prefix
  "9876 543-210"     → with spaces and dashes

Normalization steps:
  1. Remove all non-digit characters: spaces, dashes, brackets, +
  2. If starts with '91' and length > 10: strip '91' prefix
  3. If starts with '0' and length > 10: strip '0' prefix
  4. Result should be 10 digits

WhatsApp format:
  Prepend '+91': '9876543210' → '+919876543210'
  Twilio requires: 'whatsapp:+919876543210'
```

### Implementation
```typescript
// phone.ts
export function formatIndianPhoneForWhatsApp(phone: string): string {
  let digits = phone.replace(/\D/g, '')  // Remove all non-digits
  
  if (digits.startsWith('91') && digits.length > 10) {
    digits = digits.slice(2)  // Remove 91 prefix
  } else if (digits.startsWith('0') && digits.length > 10) {
    digits = digits.slice(1)  // Remove 0 prefix
  }
  
  // Now should be 10 digits
  return `+91${digits}`
}
```

## 10. Inventory Low-Stock Alert Logic

### Definition
An item is "low stock" when:
```
inventory.quantity <= inventory.low_stock_threshold
```

### Default Threshold
`5` (set via `low_stock_threshold DEFAULT 5` in the database)

### Where Alerts Appear
1. **Admin Panel Overview Dashboard** — "System Alerts" card
2. **Mobile Admin Overview Screen** — Alerts section
3. **Inventory Page** — "Low Stock" red badge on each item row

### No Automated Notification
Low stock alerts are purely visual — no push notification or email is sent when stock falls below threshold. This is a manual monitoring requirement.

## 11. Data Retention and Archiving

### Current Policy
There is **no automated data archiving** implemented. All historical data is retained indefinitely:
- All jobs (including completed, months/years old)
- All attendance records
- All salary records
- All payment records
- All notification logs
- All selfie photos in Storage

### Storage Growth Estimate
| Data Type | Growth Rate | 1-Year Volume |
|---|---|---|
| Jobs (DB rows) | ~100/month | ~1200 rows |
| Attendance photos | ~520/month | ~6240 photos (~936MB) |
| Notification logs | ~50/day | ~18,250 rows |
| Salary records | ~10/month | ~120 rows |

### Recommendation
After 1 year, implement archiving:
1. Archive completed jobs older than 12 months to a separate table
2. Delete attendance photos older than 12 months from Storage
3. Keep attendance records (DB rows) for payroll history

## 13. Material Cost Calculation

### Per Material
```
total_cost = quantity × unit_cost
```

This is calculated client-side and stored in the `job_materials.total_cost` column on INSERT.

```typescript
// AddMaterialModal.tsx
const total_cost = parseFloat(quantity) * parseFloat(unitCost)
await supabase.from('job_materials').insert({
  job_id, material_name, quantity, unit_cost, total_cost
})
```

### Parts Total (for Billing)
```typescript
// billing.ts
export const calculatePartsTotal = (materials: JobMaterial[]): number =>
  materials.reduce((sum, mat) => sum + (mat.total_cost ?? mat.quantity * mat.unit_cost), 0)
```

The `?? mat.quantity * mat.unit_cost` fallback handles cases where `total_cost` is null in the DB.

## 15. Multi-Technician Assignment

### Current Implementation
A job has ONE `technician_id` — a single technician assignment.

**If an admin reassigns:**
- The `technician_id` is updated to the new technician
- The old technician loses visibility of the job (filtered by RLS)
- The new technician does NOT automatically receive a push notification (gap — only initial assignment on creation triggers a push)

**If a receptionist reassigns via mobile:**
- Same behavior as admin reassignment
- Uses `TechnicianPicker` component

### Multi-Technician Support
Not currently implemented. If a job requires two technicians, the workaround is to add notes or split into separate jobs.
