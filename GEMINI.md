## Product summary

RepairShop is a service and repair management system for handling customer device repairs and technician operations.

The system includes:

- Mobile app for receptionist and technician workflows.
- Web admin panel for owners/admin staff.
- Supabase backend for database, authentication, storage, realtime updates, and Edge Functions.
- Attendance with selfie and GPS verification.
- Customer job intake and technician assignment.
- Job tracking with status updates.
- Onsite visit logging with arrival/departure selfie and GPS.
- Materials/parts logging.
- Billing and invoice generation.
- Salary, advance salary, and expenditure tracking.
- Inventory management.
- Push notifications, WhatsApp messages, and email notifications.
- Production deployment with RLS security.

## Non-negotiable hard rules

### 1. Server-side job code generation only

Use the PostgreSQL sequence and `generate_job_code()` function from `SKILL.md`.

Never generate job codes in:

- React Native
- React
- Next.js
- JavaScript
- TypeScript
- Client-side helper functions

This prevents duplicate job codes during concurrent job creation.

### 2. Never expose service role keys

Never place Supabase `service_role` keys in:

- Mobile app code
- Web admin code
- `.env` files intended for client bundling
- GitHub commits
- Screenshots
- Logs
- Public documentation

Service role keys are allowed only inside Supabase Edge Functions through environment secrets.

Client apps must use only anon keys with RLS.

### 3. Salary formula requires confirmation

Before implementing salary calculation code, restate the salary formula and ask the user/business owner to confirm it.

Do not implement salary logic from assumption.

Default formula from the project plan:

```text
present_pay      = present_days * base_daily_rate
halfday_pay      = halfday_count * (base_daily_rate / 2)
leave_pay        = 0
ot_pay           = ot_hours * ot_rate_per_hour
early_deduction  = early_hours * early_deduction_per_hour
gross_salary     = present_pay + halfday_pay + ot_pay - early_deduction
advance_deducted = SUM(payments.amount)
                   WHERE type = 'advance_salary'
                   AND user_id = X
                   AND month = Y
net_salary       = gross_salary - advance_deducted
```

Also confirm whether advance salary deducts only from the same month or can carry forward across months.

### 4. RLS is mandatory security, not optional polish

UI hiding is not security.

Role access must be enforced in:

- Supabase queries
- RLS policies
- Edge Functions
- Navigation guards

Do not consider a feature secure until it has been tested using separate role accounts.

### 5. No duplicated business logic

Keep business rules in the correct layer:

- Job code generation: PostgreSQL
- Notification sending: Edge Functions
- Salary calculation: confirmed server-side function
- RLS permissions: Supabase policies
- Billing formula: one shared logic pattern kept identical wherever previewed or saved

### 6. Real-device testing is mandatory

Real hardware testing is required for:

- Camera
- GPS
- Push notifications
- WhatsApp links
- Printing
- Bluetooth printers
- iOS permission prompts
- Android permission prompts

Do not mark these features complete after simulator-only testing.

## Coding standards

### TypeScript

Use TypeScript throughout.

Prefer:

- Explicit types for Supabase rows and function inputs
- Narrow union types for statuses and roles
- Shared constants for repeated status values
- Small files with clear responsibilities

Avoid:

- `any` unless absolutely necessary
- Large untyped objects
- Copy-pasted status strings across many files
- Silent catches that hide errors

### Error handling

Every Supabase operation must handle errors.

Bad:

```ts
await supabase.from('jobs').insert(payload)
```

Good:

```ts
const { data, error } = await supabase.from('jobs').insert(payload).select().single()
if (error) throw new Error(error.message)
```

User-facing errors should be clear and actionable.

### Forms

Validate required fields before database writes.

For customer contact:

- Use numeric keyboard on mobile.
- Normalize Indian numbers before WhatsApp sending.
- Strip leading `0` where required.
- Prefix `+91` before Twilio WhatsApp calls.

### UI rules

Keep UI simple and role-focused.

Use:

- Clear status badges
- Clear priority badges
- Pull-to-refresh where lists depend on live data
- Loading states
- Empty states
- Error states
- Confirmation dialogs for destructive actions

Do not silently delete critical records such as users or jobs.

### Comments

Add comments only for non-obvious business rules.

Do not fill files with comments explaining basic React or TypeScript syntax.

## Supabase rules

### Auth

After login:

1. Get Supabase Auth user.
2. Fetch row from `users` where `id = auth.uid()`.
3. Read `role` and `is_active`.
4. Route to role-specific stack.
5. Block inactive users.

Do not trust role values stored only in local state.

### Realtime

Use Supabase Realtime for job updates.

Technician subscriptions must be filtered by `technician_id`.

Do not subscribe to the whole jobs table and filter in JavaScript. That can leak other technicians' data into memory.

### Storage

Use private buckets:

- `attendance-selfies`
- `onsite-visits`
- invoice storage if generated PDFs are stored

Use signed URLs where display access is needed.

### Edge Functions

Use Edge Functions for:

- Push notification sending
- WhatsApp sending
- Email invoice sending
- Salary calculation
- Any operation requiring service role privileges

Do not call Twilio, Resend, or service-role operations from mobile or web clients.

## Module implementation rules

### Phase 1 — Project setup and auth

Implement:

- Supabase schema from `SKILL.md`
- Expo project scaffold
- Supabase client
- Auth context
- Role-based navigation
- Placeholder tabs for each role

Test before moving on:

- Admin login routes to admin stack
- Receptionist login routes to receptionist stack
- Technician login routes to technician stack
- Inactive user is blocked
- Session persists after app restart

### Phase 2 — Attendance

Build one reusable attendance screen for receptionist and technician.

Check-in flow:

1. Request camera permission.
2. Request location permission.
3. Open front camera.
4. Capture selfie.
5. Capture GPS with high accuracy.
6. Upload image to Supabase Storage.
7. Upsert attendance row.

Never submit check-in/check-out with missing GPS unless the user changes the business rule.

### Phase 3 — Receptionist dashboard

Build in order:

1. New job form
2. Receipt printing
3. Job list
4. Job detail
5. Receptionist dashboard

Important:

- Job code must come from `generate_job_code()` RPC.
- WhatsApp ready-for-pickup opens a pre-filled message only. It does not auto-send.
- Receptionist must not query salary or payments.

### Phase 4 — Technician dashboard

Technician sees only assigned jobs.

Build:

- My jobs screen
- Job detail screen
- Status update buttons
- Materials logging
- Work notes
- Onsite selfie arrival/departure flow

When status becomes `Completed`, set `completed_at`.

### Phase 5 — Notifications

Notifications belong in Edge Functions.

Required flows:

- New job assigned → push technician + WhatsApp customer
- Job status changed → push receptionist + push admin
- Job completed → WhatsApp customer if required
- Invoice email → Resend function

Log send attempts into `notifications`.

### Phase 6 — Admin panel

Build web admin pages:

- Overview
- Jobs
- Staff
- Inventory
- Reports
- Salary navigation placeholder
- Expenditure navigation placeholder
- Settings if needed

Use real Supabase data, not mock data, once the page is connected.

Admin destructive actions must require confirmation.

### Phase 7 — Billing and invoice

Use the formula exactly:

```text
grand_total = (parts_total + labour_charge) * (1 + tax_percent / 100) - discount
```

Sample verification:

```text
parts = 500
labour = 300
tax = 18%
discount = 50
expected = 894
```

Invoice branding: RepairShop.

Currency: INR.

Round money consistently to two decimal places.

Technicians must not access billing.

### Phase 8 — Salary and money

Stop before coding and ask for formula confirmation.

This phase is admin-only.

Do not allow receptionist or technician to query:

- `salary`
- `staff_rates`
- `payments`

### Phase 9 — Deployment and RLS

RLS policies must be explicit and tested.

Test security directly with separate accounts:

- Technician cannot see another technician's jobs.
- Receptionist cannot read salary or staff rates.
- Technician cannot read billing.
- Inactive user cannot use role screens.

Do not rely only on UI visibility.

- Inactive users are blocked.
- Job creation works under concurrent use.
- Status updates sync live.
- Push notifications work on real devices.
- WhatsApp messages work with real test numbers.
